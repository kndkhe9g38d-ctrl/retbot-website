RET CONTROL PANEL — SETUP

1) WEBSITE (GitHub Pages)
Upload the contents of RET-Control-Panel-Website into the GitHub Pages repository.
Edit config.js:
  API_BASE: "https://YOUR-WISPBYTE-PUBLIC-URL"

2) BOT (Wispbyte)
Upload the contents of RET-Wispbyte-Panel-Bot to /home/container.
Keep the existing root index.js token placement.

3) WISPBYTE ENVIRONMENT
Set these variables:
  RET_PANEL_CLIENT_ID=1547729921319772192
  RET_PANEL_CLIENT_SECRET=YOUR_DISCORD_APPLICATION_CLIENT_SECRET
  RET_WEB_ORIGIN=https://kndkhe9g38d-ctrl.github.io
  RET_WEB_ORIGINS=https://kndkhe9g38d-ctrl.github.io
  RET_OAUTH_REDIRECT_URI=https://YOUR-WISPBYTE-PUBLIC-URL/auth/callback

4) DISCORD DEVELOPER PORTAL
OAuth2 -> Redirects:
  https://YOUR-WISPBYTE-PUBLIC-URL/auth/callback

Scopes used:
  identify
  guilds

5) WISPBYTE PORT
Keep the HTTP/health port public. The panel API is mounted on the existing HTTP port.
Default:
  BOT_HEALTH_PORT=3000

6) SECURITY
Never put any of these in the GitHub website:
  DISCORD_BOT_TOKEN
  RET_PANEL_CLIENT_SECRET
The bot token remains server-side in the existing root index.js setup.

7) MULTI-SHARD
The panel API is intentionally exposed from shard 0 because Wispbyte normally exposes one public HTTP port.
For normal/single-shard RET deployments this is transparent.
